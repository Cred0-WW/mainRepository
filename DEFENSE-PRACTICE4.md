# Объяснение практики 4

## Что сказать о работе

Я развернул Mattermost 9.5 с MySQL 8.0, создал приватный канал с пятью
сообщениями, загрузил вложение и аватар. Затем подготовил workflow в ветке
migration. Он делает резервную копию, переносит данные через pgloader в
PostgreSQL 15 и обновляет Mattermost до 12.0.1. После переноса проверяются
исходные ID и тексты сообщений, доступность сайта и контрольные суммы файлов.
Успешный результат отмечается постоянным маркером. Повторный запуск пропускает
резервное копирование и перенос, но снова разворачивает и проверяет приложение.

## Вопросы преподавателя

**Что такое Stateful?** Приложение хранит состояние между запусками. Здесь это
пользователи, сообщения, команды, каналы и файлы.

**Почему недостаточно перенести контейнер?** Контейнер можно пересоздать,
а данные находятся в базе и Docker Volume. Их нужно сохранить отдельно.

**Что такое гетерогенная миграция?** Перенос между разными СУБД: здесь MySQL
и PostgreSQL. У них различаются SQL, типы, индексы и системные таблицы.

**Зачем pgloader?** Он читает MySQL, преобразует данные и загружает их в PostgreSQL.
Обычный MySQL SQL-дамп напрямую не подходит для PostgreSQL.

**Зачем ещё создавать PostgreSQL-схему Mattermost 9.5?** Чтобы типы колонок,
перечисления и история миграций соответствовали Mattermost. После переноса
версия 12.0.1 выполняет оставшиеся изменения собственной схемы.

**Зачем include drop и явный сброс схемы?** include drop — опция учебного
сценария pgloader, переданная в секции WITH конфигурационного файла. В нашем режиме data only таблицы уже созданы Mattermost,
поэтому повторяемость обеспечивает явное пересоздание только целевой схемы
до переноса. Это убирает частичный результат, а не дописывает дубликаты.

**Что такое идемпотентность?** Повторный запуск не переносит данные заново
и не создаёт копии сообщений; приложение остаётся в заданном целевом состоянии.
При этом служебные логи и время запуска могут меняться.

**Где маркер?** В state/.migration_completed вне рабочей папки runner.
Checkout не удаляет его. В маркере записан подтверждённый результат проверки.

**Почему маркер после тестов?** Успешный выход pgloader ещё не доказывает,
что новая версия запускается и пользователю доступны старые сообщения.

**Что будет после прерывания?** Пока маркера нет, следующий запуск повторит
бэкап и перенос из сохранённой MySQL. Целевая схема будет пересоздана.
MySQL-том и резервные копии остаются для восстановления.

**Что делает --remove-orphans?** Удаляет контейнеры того же Compose-проекта,
сервисы которых отсутствуют в новом файле. Поэтому в обоих файлах одинаковое
имя проекта mattermostpr4, а в production нет сервиса MySQL.

**Удалится ли MySQL-том?** Нет. Удаление контейнера не равно удалению тома.
Старые данные сохраняются для восстановления.

**Почему общий том?** В базе лежат сведения о файлах, а байты вложений
и аватаров — в /mattermost/data. Обе версии используют mattermostpr4_data.

**Как проверяется сохранность?** Проверяются пять исходных ID и текстов
в API и PostgreSQL, приватность канала и SHA256 вложения и аватара.

**Что такое SHA256?** Контрольная сумма. Одинаковые байты дают одинаковую сумму.
Сравнение до и после показывает, что файл не изменился.

**Где пароли?** В GitHub Secrets. Workflow передаёт их в окружение,
скрипт создаёт временный конфигурационный файл с правами 0600 и затем удаляет.
Реальные пароли и резервные дампы не включаются в артефакты.

**Зачем self-hosted runner?** Он выполняет workflow на моём Mac, где находятся
Docker, контейнеры, тома и постоянный маркер.

**Зачем concurrency?** Чтобы два запуска миграции не меняли одну базу одновременно.

**Зачем healthcheck?** Он проверяет готовность базы. Сам факт запуска процесса
не означает, что база уже принимает подключения.

**Какие порты?** Mattermost доступен на localhost:8065. Базы не публикуют порты
наружу и взаимодействуют в отдельной bridge-сети.

**Что происходит при повторном успешном запуске?** Маркер найден, шаги backup
и migrate пропущены. Выполняются deploy, verify, сбор отчётов и очистка временного
файла с секретами.

## Порядок демонстрации

1. Показать ветку migration и файл .github/workflows/migration.yml.
2. Показать два успешных запуска и пропущенные шаги второго.
3. Открыть localhost:8065 и приватный канал с пятью исходными сообщениями.
4. Открыть контрольное вложение и показать аватар.
5. Показать docker ps: Mattermost и PostgreSQL без контейнера MySQL.
6. Открыть verification.json из артефактов workflow.
