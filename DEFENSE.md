# Защита практической работы по GitHub Actions

## Что сказать в начале

«Я настроил workflow для приложения на Go с PostgreSQL. Задания выполняются на self-hosted runner моего Mac. Workflow создаёт настройки из GitHub Secrets, запускает Docker Compose и проверяет совпадение данных базы, API и таблицы в настоящем браузере. Логи, снимок страницы и отчёты сохраняются как артефакт без значений секретов».

Успешное выполнение подтверждается конкретным завершённым запуском в GitHub Actions. Для локального прогона используй формулировку «локальные проверки прошли».

## Вопросы и ответы

1. **Что такое GitHub Actions?** Платформа автоматизации GitHub. Она выполняет описанные в YAML задания при push, ручном запуске и других событиях.

2. **Что означает CI/CD в этой работе?** CI включает автоматическую проверку проекта. Этап развёртывания собирает и запускает приложение на компьютере с runner. Внешний production-сервер здесь не используется.

3. **Что такое workflow?** Весь рабочий процесс в `.github/workflows/deploy-test.yml`: события, job и последовательность шагов.

4. **Чем job отличается от step?** Job назначается runner и содержит шаги. Steps внутри моей job выполняются последовательно в одном рабочем окружении.

5. **Что такое action?** Готовый переиспользуемый компонент. Например, checkout получает исходники, а upload-artifact сохраняет файлы результатов в GitHub.

6. **Что такое self-hosted runner?** Программа-исполнитель на моей машине. GitHub передаёт ей job, и команды выполняются на Mac с доступом к Docker Desktop.

7. **Зачем нужны четыре метки runner?** `self-hosted` выбирает собственный runner, `macOS` — систему, `ARM64` — архитектуру, `github-actions-lesson` — экземпляр для этой работы. Должны совпадать все метки.

8. **Почему runner ephemeral?** Он принимает одну job и после неё снимается с регистрации. Для следующего запуска нужен новый зарегистрированный экземпляр. Это не означает удаления Docker-контейнеров приложения.

9. **Когда запускается workflow?** При push в `main` или вручную через `workflow_dispatch`. Runner выполняет команды на компьютере, поэтому запускать следует свой проверенный код.

10. **Где находятся пароли?** В Repository Secrets GitHub. Шаг получает их через переменные окружения и записывает рабочий `.env` с правами `0600`. Пароль не записан в YAML или исходниках.

11. **Почему в артефакте есть `.env`, но нет пароля?** Это отдельная копия, в которой каждое значение заменено на `***`. Рабочий файл с настоящими значениями не загружается.

12. **Зачем проверять файлы перед upload, если GitHub маскирует Secrets?** Маскирование журнала не очищает загружаемые файлы. Helper самостоятельно редактирует секреты и проверяет итоговые файлы до загрузки.

13. **Почему используется `docker compose`, а в задании написано `docker-compose`?** Это современная команда Compose в Docker CLI. Она запускает те же сервисы, а `--wait` позволяет дождаться готовности без фиксированной задержки.

14. **Какие контейнеры запускаются?** `app` с Go-сервером и `db` с PostgreSQL. Приложение открыто на локальном порту 8082; порт базы на компьютер не опубликован.

15. **Как приложение находит базу и сохраняет данные?** По имени сервиса `db` в сети Compose. Файлы базы находятся в томе `githubactionslesson_db_data`, который сохраняется при обычной остановке и пересоздании контейнеров.

16. **Что доказывает тест браузера?** Тест читает записи независимым SQL-запросом, получает API-ответ и считывает реальные ячейки таблицы Chromium. Сравниваются все ID и названия; совпадения одного количества строк недостаточно.

17. **Как проверяется работа приложения и соединения с БД?** `/healthz` должен вернуть `200` и `ok`. Этот обработчик проверяет PostgreSQL. Дополнительно тест читает базу напрямую и обращается к API.

18. **Что будет при ошибке теста?** Команда завершится с ненулевым кодом, job будет неуспешной. Сбор диагностики всё равно выполняется через `if: always()`, а upload разрешён только после успешной проверки безопасности файлов.

19. **Для чего нужны concurrency, timeout и commit SHA?** Concurrency ограничивает одновременные развёртывания на одном порту. Timeout ограничивает время job. Полный SHA фиксирует конкретную версию action вместо подвижного тега.

20. **Как отличить GitHub run от локальной проверки?** У GitHub run есть URL, номер запуска, commit, имя runner, статус job и раздел Artifacts. Локальный скрипт создаёт отчёт с режимом `local` и не подтверждает регистрацию runner или upload в GitHub.

## Настройки workflow по порядку

| Строка или блок | Краткое объяснение |
|---|---|
| `name: Docker Compose deployment and browser tests` | Название на вкладке Actions. |
| `on:` | Начало списка событий запуска. |
| `push:` и `branches: [main]` | Запуск при изменениях в main. |
| `workflow_dispatch:` | Разрешает ручной запуск. |
| `permissions: contents: read` | Даёт GITHUB_TOKEN только чтение репозитория. |
| `concurrency:` | Ограничивает параллельные запуски группы. |
| `cancel-in-progress: false` | Новый запуск не отменяет уже выполняющийся. |
| `jobs:` | Начало описания заданий. |
| `deploy-and-test:` | Идентификатор единственной job. |
| `runs-on: [self-hosted, macOS, ARM64, github-actions-lesson]` | Выбирает runner со всеми этими метками. |
| `timeout-minutes: 20` | Ограничивает job двадцатью минутами. |
| `defaults: run: shell: bash` | Задаёт bash для команд run. |
| `env:` | Переменные окружения соответствующего job или step. |
| `COMPOSE_PROJECT_NAME: githubactionslesson` | Отдельное имя ресурсов этой работы. |
| `CI: "true"` | Сообщает инструментам об автоматическом запуске. |
| `steps:` | Начало последовательности шагов. |
| `uses: actions/checkout@<SHA>` | Получает исходники по конкретной версии action. |
| `persist-credentials: false` | Не сохраняет token для следующих git-команд. |
| `uses: actions/setup-python@<SHA>` | Подготавливает Python для helper-скрипта. |
| `python-version: "3.12"` | Выбирает Python 3.12. |
| `uses: actions/setup-node@<SHA>` | Подготавливает Node.js и npm. |
| `node-version: "22"` | Выбирает Node.js 22. |
| `cache: npm` | Кэширует загруженные npm-зависимости по lock-файлу. |
| `run: \|` | Позволяет записать несколько shell-команд в одном шаге. |
| Запись Docker bin в `$GITHUB_PATH` | Делает Docker CLI доступным следующим шагам. |
| `docker info` и `docker compose version` | Проверяют Docker Desktop и Compose. |
| `DB_PASSWORD: ${{ secrets.DB_PASSWORD }}` | Передаёт секрет в окружение без вставки в shell-код. |
| `python3 scripts/ci.py create-env` | Проверяет параметры и создаёт рабочий `.env`. |
| `npm ci` | Устанавливает версии из package-lock.json. |
| `npx playwright install chromium` | Устанавливает браузер для тестов. |
| `docker compose config -q` | Проверяет конфигурацию, не печатая её значения. |
| `docker compose up -d --build --wait --wait-timeout 120` | Собирает приложение, запускает сервисы в фоне и ждёт готовности до 120 секунд. |
| `docker compose ps` | Показывает состояние контейнеров проекта. |
| `APP_PORT: ${{ secrets.APP_PORT }}` у тестового шага | Передаёт тестам порт проверяемого приложения. |
| `npm test` | Выполняет проверки Playwright. |
| `id: evidence` | Даёт шагу сбора имя для проверки результата. |
| `if: always()` | Выполняет диагностику даже после ошибки предыдущего шага. |
| `python3 scripts/ci.py collect` | Собирает логи, состояние, отчёты и маскированный `.env`, проверяет отсутствие секретов. |
| `steps.evidence.outcome == 'success'` | Запрещает upload при неуспешной безопасной подготовке. |
| `uses: actions/upload-artifact@<SHA>` | Сохраняет подготовленные файлы в GitHub. |
| `name: deployment-${{ github.run_id }}-${{ github.run_attempt }}` | Включает номер запуска и попытки в имя артефакта. |
| `path: artifacts/` | Загружает только папку подготовленных результатов. |
| `include-hidden-files: true` | Включает маскированный файл `.env`. |
| `if-no-files-found: error` | Считает отсутствие файлов ошибкой. |
| `retention-days: 30` | Задаёт срок хранения. |
| `python3 scripts/ci.py summary` | Формирует сводку фактических результатов. |
| `python3 scripts/ci.py clean-env` | Удаляет только рабочий `.env`, созданный helper. |

Полные SHA находятся в workflow. Обозначение `<SHA>` здесь используется для краткого пояснения.

## Порядок показа преподавателю

1. Открыть `.github/workflows/deploy-test.yml`, показать события, runner и получение Secrets.
2. На GitHub открыть конкретный run, показать commit, runner и результат шагов.
3. Открыть http://localhost:8082 и `/api/items`.
4. Показать `tests/browser.spec.mjs`: SQL-запрос, API и сравнение с DOM.
5. Скачать артефакт из этого run, показать `test-report.md`, `data-comparison.json`, логи и маскированный `.env`.

## Полезные команды

```sh
# Полный локальный запуск и браузерные проверки.
sh scripts/run-local.sh

# После локального запуска: состояние и последние сообщения приложения.
docker compose ps
docker compose logs --tail 30 app

# Проверки работающего приложения.
curl --fail http://localhost:8082/healthz
curl --fail http://localhost:8082/api/items

# Остановка с сохранением данных.
docker compose stop
```

Результат относится к конкретному прогону. Online у runner, успешный job и загруженный артефакт показываются по фактическим сведениям GitHub.
